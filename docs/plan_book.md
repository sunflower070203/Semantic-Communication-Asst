# 项目策划书：语义通信助手（Semantic Communication Assistant）

> 赛道一：AI Agent 应用创新赛（OpenTrek 平台）
> 团队成员：孙浩（东南大学）
> 最后更新：2026-08-24

## 1. 项目背景与痛点

语义通信是 6G 与通信-人工智能深度融合的核心方向，论文数量快速增长，但研究门槛集中在三个环节：

1. **找文献难**：方向分散（Deep JSCC / DeepSC / 任务导向通信 / 语义信息论…），关键词多样，
   新手不知道从哪篇经典论文切入；
2. **读文献难**：论文概念密集、互相引用，读完一篇要回溯多篇；
3. **引用可信度难验证**：通用大模型问答不区分领域、不给文献来源，回答里的"事实"无法核对原文，
   科研场景下不敢直接用。

本项目的核心洞察：**科研问答的可靠性不来自模型，而来自"可溯源的检索 + 程序化的引用校验"**。

## 2. 项目目标

构建一个面向语义通信/泛 CS 领域的**文献问答智能体**，做到：

- 基于精选领域知识库（10 篇核心论文，全文明文解析）回答问题；
- 回答带**页码级引用**，每条引用可溯源到原文；
- **程序化校验引用真实性**：正文标记 ↔ 引用列表 ↔ 召回 chunk 三方一致，未通过显式标注；
- 双形态交付：**知识库问答工作流（主推）** + **角色对话自主 Agent（备选）**；
- 开箱即用：线上分享链接，无需本地环境即可体验。

## 3. 目标用户与使用场景

| 用户 | 场景 |
|---|---|
| 通信方向研究生 | 快速搞清概念、拿到出处，直接进原文 |
| 跨方向科研人员 | 从零进入语义通信领域，按主题渐进提问 |
| 评审/参观者 | 直接对话体验，观察"检索→总结→引用溯源→校验"全链路 |

## 4. 技术方案

### 4.1 总体架构（基于东南大学 OpenTrek 平台，学校指定）

```
用户提问
  → B 路线：语义通信知识问答（确定性工作流，主推）
      多轮改写 → 文档召回（知识库向量检索+重排）
      → 结果总结（LLM，JSON 结构化输出：answer + refs）
      → 引用校验（脚本节点，程序化断言） → 带引用的最终回答
  → A 路线：语义通信自主 Agent3（角色对话，AutoBotV2 + ReAct）
      角色定义 + 自主规划与总结；工具已预注册（执行器受平台沙箱限制）
```

### 4.2 领域知识库

- 平台文档知识库（kbCode `ryekr4gqw2pn`），10 篇语义通信核心论文，10/10 解析成功；
- 覆盖奠基（DeepSC / Deep JSCC / 语义通信综述 / 语义通信理论）、扩展（视频/文本/SNR 自适应/
  语义重要性 JSCC）、理论（语义通信数学理论）三档；
- 解析产物带 `file_code + 页码 + 版面坐标` 元数据，是"引用可溯源到页"的数据基础；
- 全链路 API 化：STS 临时凭证 → minio 预签名 PUT → 注册解析（`scripts/kb_upload.py`），
  后续扩方向（泛 CS 文献）可脚本批量灌库。

### 4.3 B 路线：确定性工作流（主推，已发布 ONLINE）

11 节点 10 边，核心设计：

1. **多轮改写**：结合会话历史把追问补全为独立问题，驱动检索；
2. **文档召回**：向量检索 + rerank，输出带元数据的 chunk；
3. **结果总结**：LLM 按 JSON Schema 输出 `answer + refs`，refs 的 idx 必须对应召回内容；
4. **引用校验（创新点）**：脚本节点容错解析总结 JSON，断言
   - 每个引用 idx 真实存在于本次召回 chunk；
   - 正文每个 【X】 标记都有对应 refs 条目；
   - 未通过输出 `⚠ 引用校验：[...] 未能与本次召回内容核实`，**不掩盖、不静默**。

这把"模型输出不能直接成为事实"落成程序行为，是 RAG 应用深度的关键体现。

### 4.4 A 路线：自主 Agent（备选，已发布 ONLINE）

- 角色对话型（AutoBotV2）+ processAgentEngine/ReAct，qwen3.6-plus；
- 具备自主规划、任务拆解与总结能力，适合自由对话与观点组织；
- 工具（联网搜索 MCP、数学计算器等）**已注册**，但平台工具执行沙箱后端故障
  （`AGENT_TASK_DEFAULT_FAILED` / `taskBeforeConfig is null`，8/23 与 8/24 两次实测复现），
  属于平台侧天然约束；待平台修复后即可闭合"思考→动作→观察"循环。

### 4.5 工程化与可复现评测（技术质量分核心证据）

- **确定性 eval**（`scripts/eval_agent.py`）：3 个场景（概念/多步/越界联网），
  断言回答存在、无流程错误、引用一致、校验干净、拒绝编造、无任务失败；平台抖动自动重试一次；
- **对抗探针**（`scripts/probe_agent.py`）：多步任务、联网越界、跨轮追问，检验"是不是真 Agent"；
- **引用校验节点单测**（`scripts/test_validation_logic.py`）：负路径（伪造引用/标记缺失/非法 JSON）
  全部有断言，不依赖平台；
- **发布纪律**：ONLINE 配置冻结，`deploy_flow.py` 自动化克隆-补丁-保存-上线，杜绝版本漂移。

## 7. 创新点与亮点

1. **引用三级校验**：正文标记 ↔ refs ↔ 召回 chunk（含页码），程序化断言，失败显式标注——
   解决科研问答"引用不可信"的核心痛点；
2. **页码级溯源**：回答引用可定位到论文具体页与版面位置；
3. **可复现评测体系**：确定性 eval + 对抗探针 + 校验节点单测，把"演示过"变成"回归可验"；
4. **双引擎架构**：确定性工作流（可靠）与自主 Agent（灵活）互补，覆盖不同演示场景；
5. **全流程 API 化**：知识库灌库、Agent 发布、评测一键脚本，为扩方向（泛 CS）留自动化通道。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台工具执行沙箱后端故障 | A 路线无法实时检索外部文献；Function Calling 深度受限 | 主推 B 路线知识库问答；A 路线展示自主规划与引擎就绪；策划书如实披露 |
| 脚本沙箱禁网 | 流程内不能调外部 API | 检索全部收敛到平台知识库节点 |
| 设计页二次访问白屏（平台 bug） | 改配置困难 | 配置完成后不再进入设计页；要改就走 clone 新版本 |
| 论文解析失败 | 召回覆盖下降 | 根因是源 PDF 损坏，已用有效版本 API 补传；解析状态可轮询 |
| 会话凭据过期 | 自动化脚本中断 | 凭据入 `.env`，过期可从浏览器刷新；脚本对 401 快速失败 |
