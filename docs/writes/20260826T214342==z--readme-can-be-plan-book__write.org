#+title:      README 当策划书交？能，除非你不想过审
#+date:       [2026-08-26 Wed 21:43]
#+filetags:   :write:
#+identifier: 20260826T214342
#+author:     李继刚

先说结论：不能。README 是门面，策划书是论证。把 README 当"项目策划书与设计方案"交上去，
等于把"为什么做这个、凭什么它能赢、你想没想清楚"全部丢给评委自己猜。评分表里
30% 创新性、20% 文档完整性，全是论证分，README 一个字都没论证。

第一刀。这两份文件不是详略关系，是物种关系。README 回答"它是什么"——特性列表、截图、
快速开始，给来看热闹的人。策划书回答"为什么值得做、怎么做、凭什么能做成"——给要给你
打分的人。评分表文档栏写的是"项目策划书质量、技术文档、演示视频"，策划书三个字在评分表
里出现，README 不在。你拿 README 去顶，评委翻到文档栏找不到对应物，只能按"没有"给分。

第二刀。再往下。README 里能放的，策划书里也能放；但策划书有三样东西 README 永远不会有——
痛点论证、风险披露、计划与分工。这三样不是格式要求，是评委判断"这人想没想清楚"的窗口。
我们这一路踩的坑：工具执行沙箱后端故障、脚本禁网、平台没有原生生图、ONLINE 配置冻结、
知识库源 PDF 损坏。这些放进 README 是一行"平台约束"，放进策划书是一整节"风险与应对"，
而且是我们最值钱的诚实材料。评委问"工具用不了，你的 Function Calling 怎么做"，你指 README
那一行字，和指策划书里完整的替代方案，是两种结果。一个让人觉得你在遮掩，一个让人觉得
你想得比平台还远。

第三刀。再剖一层。README 为什么看起来"够用"？因为它把架构图、特性、截图都放进去了，
而这些东西确实是策划书的血肉。可策划书的骨头不是这些。骨头是论证链：痛点是否真实 →
方案是否对症 → 深度体现在哪 → 怎么证明不是演示幻觉 → 万一平台不给力怎么办。README
是这条链的最后一环——成品展示；前面四环它全没有。拿 README 交付，等于交了一份只有
结论没有推导的答卷。推导过程才是 50% 的分数。

切到底。但你的问题其实已经解决了。docs/plan_book.md 就是策划书，8/24 我按评分点重写过：
痛点（科研找/读文献）、引用三级校验与页码溯源、双引擎架构、可复现 eval、平台约束风险表、
与评分标准逐项对照表。所以真实的问题不是"要不要写"，是"提交的时候别拿错文件"。
README 留着当开源门面，plan_book.md 转成 PDF 或 Word 交上去。别偷懒，别用"仓库已经很
完整了"说服自己——评委不看仓库，看提交清单。

合起来看。README 能交付吗？能——如果你只想要一个好看的 GitHub 仓库。要过审，不行。
好在两个我们都有，用对的那个就行。

说实话，这件事本身挺有意思：人最容易在最后一步省掉最不该省的东西。文件就在那里，
转个格式，十分钟的事。
